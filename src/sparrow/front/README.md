# Front (Sparrow Route)

React-фронт, ходит в FastAPI/SQLite через Vite proxy.

## Запуск

Терминал 1 — бэк:
```bash
cd back
source .venv/bin/activate
uvicorn app.main:app --reload --port 8000
# по желанию: curl -X POST http://localhost:8000/api/v1/seed
```

Терминал 2 — фронт:
```bash
cd front
npm install
npm run dev
```

http://localhost:5173 · proxy `/api` → `:8000`

## Тестовый вход

Только администратор: `admin` / `admin`. Авторизация локальная, без проверки бэкендом.

## Сценарий

- При первом открытии админ-панели создаётся один демонстрационный результат автоматического поступления. Подробности см. в разделе [Автоматическое поступление](#автоматическое-поступление).
- Если автоматическое поступление не сработало, администратор может вручную загрузить PDF / DOCX / TXT или вставить текст обследования, указав данные пациента.
- Бэкенд извлекает и структурирует данные, затем рассчитывает маршрут и возвращает его в очередь проверки.
- Администратор проверяет и при необходимости редактирует результат. Изменение сохраняется через `PATCH /api/v1/routes/{id}` и возвращает запись в очередь.
- Подтверждение вызывает `POST /api/v1/routes/{id}/approve`. Передача клиенту пока заглушечная: сведения о доставке записываются в `localStorage` и отображаются в блоке «Передано клиентам».

## Автоматическое поступление

Автоматическое поступление сейчас имитируется фронтендом. Это не подключение к медицинской системе: приложение не получает реальные события, не опрашивает внешний сервис и не следит за папкой с файлами.

### Как проходит демонстрационный сценарий

1. После открытия админ-панели React запускает обработчик автоматического поступления.
2. Фронтенд создаёт встроенный пример обследования для демонстрационного пациента. Имя файла примера — `system-upload-stub.txt`; данные включают жалобы, тревожные признаки и результат анализа.
3. Пример отправляется через `POST /api/v1/routes`. В запросе включён `force_decide`, поэтому бэкенд выполняет расчёт маршрута.
4. Полученный маршрут показывается в очереди администратора со статусом ожидания проверки. Статус обработки виден в панели «Автоматическое поступление».
5. После успешного создания ID маршрута сохраняется в браузере под ключом `sparrow_auto_result_route`. При следующих открытиях эта же демонстрационная запись повторно не создаётся.

### Ошибки и повтор

Если запрос к бэкенду завершается ошибкой, текст ошибки показывается в панели автоматического поступления, а ID не сохраняется. Кнопка «Повторить поступление» запускает попытку снова. Для обработки нужен запущенный backend на `localhost:8000`.

Чтобы заново увидеть демонстрационный сценарий в том же браузере, удалите ключ `sparrow_auto_result_route` из `localStorage` и обновите страницу. Удаление ключа не удаляет уже созданный маршрут из базы данных: повторная попытка может создать ещё одну запись.

### Подключение реального источника

Для реального поступления потребуется заменить встроенный пример интеграцией с источником обследований: например, серверным webhook или API-очередью. Такой интеграции в текущем проекте нет. Реальный источник должен передать данные пациента и документы; далее их следует сохранить и отправить по серверному конвейеру обработки, а результат вернуть в очередь проверки администратора.

Основные вызовы: `GET /api/v1/routes`, `GET /api/v1/patients`, `POST /api/v1/routes`, `PATCH /api/v1/routes/{id}`, `POST /api/v1/routes/{id}/approve`, `DELETE /api/v1/routes/{id}`.

Клиент API: `src/api/routesApi.js`
